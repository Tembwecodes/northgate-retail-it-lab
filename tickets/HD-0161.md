HD-0161: Mapped Network Drive Fails to Reconnect After Reboot
Category: Desktop Support Priority: Standard Status: Resolved

Summary
Investigated why a mapped network drive can fail to reconnect automatically after a reboot, a common real-world Tier 1 ticket. Extensive cross-VM setup (NAT Network vs Internal Network alignment between Win11-TroubleshootVM and DC01, credential scoping, network profile settings) kept resulting in the drive reconnecting successfully rather than reproducing the fault live, so this ticket documents the general failure mechanisms behind the symptom rather than a single forced repro.

Problem
A mapped network drive that works fine during an active session can fail to show as connected after the next reboot, appearing with a red X in File Explorer or requiring the user to manually reconnect. Set out to reproduce and document this against DC01 as the remote share host.

Discovery
Worked through several potential causes systematically:

Verified network configuration alignment between Win11-TroubleshootVM and DC01 (NAT Network vs Internal Network mismatch would prevent the share from being reachable at boot at all).

Checked how credentials for the mapped drive were being cached, credentials saved under an elevated session are scoped differently (HKCU:\Network) than a standard user session, which can cause a drive mapped as one to silently fail to reconnect as the other.

Checked DC01's network profile, a share host set to a Public network profile blocks File and Printer Sharing by default, which would prevent client reconnection regardless of the mapping itself.

Confirmed that authenticating with a domain-qualified account (NORTHGATERETAIL\Administrator rather than just Administrator) was required for the mapping to authenticate correctly against DC01.

Despite working through all of the above, the drive kept reconnecting successfully after reboot in this environment, the share (Everyone: Full Access, no NTFS restriction) was permissive enough that even without a cleanly cached credential, the reconnect succeeded, so the specific fault couldn't be forced live in this lab setup.

Fix
Documented the ticket based on the known general failure mechanisms for this class of issue rather than a live repro:

* Saved credentials being cleared or never cached in the correct scope
* Hostname/DNS not yet resolvable at the point in boot the reconnect is attempted (a timing race between network readiness and drive-reconnect attempts)
* The network adapter not yet being "ready" (past a metered/unidentified state) when Windows attempts the reconnect during startup

Verification
Confirmed the drive did reconnect successfully across multiple reboot tests in this environment, and cross-checked the documented failure mechanisms against how Windows handles persistent drive mappings and credential caching generally.

Root Cause
Mapped network drives reconnect at logon by re-authenticating against the host using cached credentials and DNS/network availability at that point in the boot sequence; if any of those (saved credentials, name resolution, adapter readiness) aren't in place at the right moment, the reconnect silently fails even though the same drive maps successfully once the user is fully logged in and the network is settled.

Resolution
* Ruled out network configuration mismatch, network profile restrictions, and non-domain-qualified credentials as causes in this environment
* Confirmed the test share's permissive NTFS/share settings meant the specific credential-caching fault couldn't be forced live
* Documented the standard fix set for this class of issue: re-saving credentials via a Persistent mapping with the "Remember my credentials" option checked, and adding a short login-script delay or retry where boot-time timing races are suspected

Lessons Learned
* Not every ticket can be reproduced cleanly in a lab environment, sometimes the environment is more permissive than production and won't surface the fault; documenting the known mechanisms is still valuable
* Elevated vs standard-session credential caching (HKCU:\Network scoping) is a real and easy-to-miss cause of "works when I'm logged in, fails on reboot" drive issues
* A share host's network profile (Public vs Private/Domain) affects client reconnection independently of the share and NTFS permissions themselves
