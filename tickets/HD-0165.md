HD-0165: No Sound Output, Audio Device Disabled
Category: Desktop Support Priority: Standard Status: Resolved

Summary
Win11-TroubleshootVM had no audio output, simulating the kind of audio/display regression that can follow a Windows update. Diagnosed via Get-PnpDevice that the audio endpoint had been disabled, fixed by re-enabling it through Device Manager.

Problem
Simulated a no-sound fault, framed as the kind of issue that can turn up after a Windows update silently disables or rolls back a driver. Chose to reproduce it via a disabled audio device rather than a display fault for this scenario.

Discovery
Checked baseline audio devices first via Get-PnpDevice -Class AudioEndpoint to confirm what should be present (Microphone and Speakers, both High Definition Audio Device).

Attempted to disable the Speakers device directly via a filtered PowerShell pipeline:

Get-PnpDevice -Class AudioEndpoint | Where-Object { $_.FriendlyName -like "Speakers*" } | Disable-PnpDevice -Confirm:$false

This failed with a generic CIM/WMI failure (HRESULT 0x80041001) rather than disabling the device, PnP device state changes like this don't reliably go through the CIM-based Disable-PnpDevice cmdlet when piped from a filtered device object in this environment.

Re-ran Get-PnpDevice -Class AudioEndpoint afterward and confirmed both devices showed Status: Unknown, consistent with the device having been left in an inconsistent state by the failed pipeline attempt rather than cleanly disabled.

Fix
Disabled and re-enabled the audio device directly through Device Manager's GUI instead of the PowerShell pipeline, which reliably changes device state where the piped cmdlet call did not.

Verification
Ran Get-PnpDevice -Class AudioEndpoint again and confirmed both the Microphone and Speakers devices showed Status: OK, then confirmed audio output worked correctly through the re-enabled device.

Root Cause
The audio endpoint device had ended up in a disabled/inconsistent state (simulating the effect of a driver rollback or disablement after a Windows update); attempting to force the state change via a filtered Disable-PnpDevice pipeline call failed outright in this environment rather than cleanly toggling the device, requiring the GUI route instead.

Resolution
* Captured a baseline device list via Get-PnpDevice -Class AudioEndpoint before making changes
* Attempted to disable the device via a filtered PowerShell pipeline, which failed with a CIM/WMI error and left devices in an Unknown status
* Disabled and re-enabled the audio device via Device Manager instead
* Confirmed via Get-PnpDevice that both audio devices returned to Status: OK and that sound output was restored

Lessons Learned
* Disable-PnpDevice piped from a filtered Get-PnpDevice object doesn't reliably work in every environment, a CIM/WMI failure here doesn't necessarily mean the device itself is faulty
* Device Manager's GUI toggle is a more reliable fallback than scripted PnP state changes when a cmdlet call fails outright
* Checking Get-PnpDevice status before and after a fix (OK vs Unknown) is a clean, quick way to confirm a device state change actually took effect
