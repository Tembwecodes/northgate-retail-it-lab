HD-0159: Login Failure Due to Corrupted User Profile
Category: Desktop Support Priority: Standard Status: Resolved

Summary
User "admin" on Win11-TroubleshootVM (machine troubleshoot-pc) could authenticate but was logged in with a temporary profile instead of their normal desktop and settings, a classic corrupted-profile pattern. Simulated by breaking the profile's registry key directly, then fixed by restoring the correct key and clearing the temporary profile Windows had created in the meantime.

Problem
Simulated a profile corruption fault for the local "admin" account (SID S-1-5-21-2604532397-4121623133-2751387619-1001). Login succeeded, but the user would be dropped into a temporary profile, missing their usual desktop, settings, and files.

Discovery
Corrupted the profile deliberately for the simulation by renaming the account's ProfileList registry key (under HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList) to end in .bak, this is the mechanism Windows itself uses internally when it detects a profile it can't load cleanly, so reproducing it manually gave a realistic fault.

Renaming that key wasn't straightforward, ProfileList keys are owned by SYSTEM/TrustedInstaller by default, so even an elevated PowerShell session couldn't rename it directly. Had to first take ownership of the key via regedit's Advanced Security Settings before the rename would go through.

After logging in again with the profile key renamed, Windows created a new temporary profile key for the same SID, exactly the "logged in but nothing is there" symptom the ticket described.

Fix
Deleted the erroneous temporary profile key Windows had created for the SID, then renamed the original backed-up key (ending in .bak) back to its correct SID name, restoring it as the account's real profile registry entry.

Verification
Logged in again as "admin" and confirmed the user's normal desktop, settings, and files loaded correctly, not a fresh temporary profile.

Root Cause
The account's ProfileList registry key had become inaccessible under its correct SID (simulated here via a rename), causing Windows to detect the profile as unusable and fall back to creating a temporary one at each login instead of loading the real profile.

Resolution
* Took ownership of the ProfileList registry key via Advanced Security Settings, since it's owned by SYSTEM/TrustedInstaller by default
* Identified and deleted the temporary profile key Windows had created for the SID after the simulated corruption
* Renamed the backed-up original profile key back to its correct SID, restoring the real profile
* Confirmed the user's normal profile loaded correctly on next login

Lessons Learned
* A user logging in successfully but landing on an empty/temporary desktop is the signature symptom of profile corruption, worth checking ProfileList in the registry early
* ProfileList keys need an ownership change via Advanced Security Settings before they can be renamed, even from an elevated session
* Windows creates a new temporary profile key automatically once it can't load the real one, that temporary key needs deleting as part of the fix, not just restoring the original
