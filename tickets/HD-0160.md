HD-0160: Shared Folder Access Denied Despite Visible Share
Category: Desktop Support Priority: Standard Status: Resolved

Summary
A shared folder was visible and browsable over the network but returned "Access is denied" when opened. Traced to an explicit NTFS Deny permission overriding share-level access, fixed by removing the Deny entry rather than adding a competing Allow.

Problem
Simulated an access-denied fault on a test shared folder, the share itself was visible and browsable from the network, but attempting to open it returned "Access is denied."

Discovery
Checked the share permissions first, these looked fine and didn't explain the block, so moved on to checking NTFS permissions directly on the folder. Found an explicit Deny entry for Everyone applied at the NTFS level (icacls showing (DENY)(F) for Everyone), this was the injected fault, and Deny always overrides Allow in NTFS regardless of what the share permissions say.

Fix
Removed the Deny entry directly rather than adding a new Allow permission alongside it:

icacls "C:\path\to\folder" /remove:d Everyone

Adding a competing Allow entry wouldn't have helped, an explicit Deny takes precedence over any Allow for the same identity.

Verification
Confirmed via icacls that the Deny entry was gone, then reconnected to the share from the client side and confirmed the folder opened normally with no access error.

Root Cause
An explicit NTFS Deny permission for Everyone had been applied directly on the folder, which overrides any Allow permission (share-level or NTFS) for the same account or group, this is standard NTFS precedence behaviour, not a share configuration fault.

Resolution
* Ruled out share-level permissions as the cause by checking them first
* Found an explicit NTFS Deny entry for Everyone via icacls
* Removed the Deny entry directly rather than layering an Allow on top of it
* Confirmed the share opened normally afterward

Lessons Learned
* When share permissions look correct but access is still denied, check NTFS permissions on the folder itself next, the two are independent and both apply
* An explicit NTFS Deny always overrides an Allow for the same identity, so the fix is to remove the Deny, not add a competing Allow
* icacls /remove:d targets Deny entries specifically, useful for surgical permission fixes without disturbing existing Allow entries
